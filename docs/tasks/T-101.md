## Reglas, invariantes y errores

Fill posterior a cancel request actualiza ledger y exposición correctamente

Conservar INV-01–INV-18 aplicables. Identidad y unidad nunca se infieren de un ticker. Un resultado desconocido no se convierte en 0/false/éxito. Repetición del mismo input no duplica efectos. Fallo de persistencia no confirma comando mutante. Propagar error saneado y código estable; retry sólo dentro de política y deadline.

## Procedimiento

1. Leer HEAD/estado local e instrucciones, resolver dependencias y localizar archivos afectados.
2. Congelar fixture mínimo positivo y el caso negativo descrito arriba, con resultado esperado independiente.
3. Implementar el puerto/caso de uso/adaptador necesario, sin ampliar capacidades externas.
4. Añadir prueba del límite y del error; verificar permisos y efectos idempotentes si existe mutación.
5. Ejecutar checks del módulo, contrato e integración pertinente; revisar diff y generar evidencia.

## Pruebas unitarias y de integración

Añadir fronteras de cantidad/tiempo/tamaño y input incompleto. ## Aceptación y Definition of Done

**AC-101**: objetivo demostrado por fixture positivo, caso negativo produce rechazo/estado esperado y ninguna invariante queda violada; contrato y permisos pasan; revisión del diff no contiene alcance ajeno. DONE sólo con pruebas ejecutadas, output/exit codes y dependencias verificadas. Si falla evidencia financiera, registrar REJECTED/INCONCLUSIVE sin ajustar criterio silenciosamente.

Evidencia: reporte conforme a `evidence.schema.json`, commit base/final, archivos, comandos, logs saneados, versiones, fixtures y limitaciones. Guardar en `evidence/T-101/` del futuro repo. Esfuerzo orientativo: 0.5–2 días de implementación; datos/ensayos prospectivos aparte.
